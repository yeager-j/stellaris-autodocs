# Decode source textures through a pinned conversion recipe

`image_dds` is an accepted dependency for decoding DDS textures, at `0.7.2` with `default-features = false, features = ["ddsfile"]`. The asset module's decoder adapter converts a surface into the application-owned decoded image and is the only place an `image_dds` type appears. Conversion is governed by a versioned Recipe value holding the mip level, layer policy, colorspace declaration, alpha policy, output format, encoder identity, and decoded-size limit; every asset key derives from the source bytes plus that recipe's canonical encoding. This choice is reversible at the cost of one module: nothing above the adapter names `image_dds`, and the decoded-image and outcome types are defined without reference to it.

Encoding is disabled deliberately. The crate's default `encode` feature depends on `intel_tex_2`, which compiles through the Intel ISPC compiler and ships no precompiled kernels for every target named in [ADR 0005](0005-develop-on-macos-with-a-three-platform-release-target.md). Decoding never needs it. Disabling it also removes `image_from_dds`, which is the API the adapter must not use: it decodes every array layer and stacks them vertically, so a 2048×2048 cube map returns as a 2048×12288 image with no error and nothing in the result to make a caller doubt it. The adapter calls `Surface::decode_layers_mipmaps_rgba8` with an explicit single layer and single mip instead, because layer and mip selection are the recipe's decisions and not a helper's defaults. The [DDS evaluation](../spikes/dds-evaluation.md) measured this against 33,145 files.

Two shapes are refused rather than decoded, and the refusals are normative. Any surface with more than one array layer is `UnsupportedFormat`, because choosing a cube-map face silently would be a presentation decision made inside a decoder; all twelve cube maps in the pinned corpora are absent from the reachable set, so the refusal costs nothing today. `DXT2` and `DXT4` are `UnsupportedFormat` because they carry premultiplied alpha that `image_dds` maps to BC2 and BC3 without un-premultiplying; neither occurs locally, and decoding them under a straight-alpha recipe would produce a quietly wrong image rather than a visible failure.

The outcome contract is a closed set of four, and which rule decides each one is part of the contract. `MalformedMedia` and `UnsupportedFormat` are decided by lookups over what the container declares — the application-owned DDS header reader, the recipe's shape policy, and the adapter's supported-format set — before any decoding runs. `ConversionFailure` is the only outcome that indicts the adapter rather than the input. Keeping them apart is what lets `analysis::finalize` scope its Analysis Issue: if both refusals reduced to *the decoder returned an error*, a placeholder for an unreadable file and a placeholder for an unsupported format would be indistinguishable. The header reader is therefore written from the DDS specification rather than through `ddsfile`, even though `image_dds` already depends on it.

The recipe version cannot be a hand-maintained integer alone. `image_dds` decodes the compressed classes through `bcdec_rs`, so a transitive bump there changes output pixels with no first-party change; and one identical decoded image encoded eight ways through one version of `png` produced six distinct digests, so encoder settings change output bytes without changing a pixel. The recipe therefore records the resolved decoder and encoder versions and their settings, and any semantic change to any field changes every derived asset key. Output is PNG through the `png` crate named directly rather than through a re-exporter whose defaults can move independently of its own version. Lossless WebP measured 7% smaller and remains available additively, because `output_format` is already a key component.

The residual risk is that correctness here is silent when it fails. A decoder that exchanges red and blue returns a plausible image, and only eleven files in the corpus declare the channel order that would expose it. The application cannot detect this at runtime, so the protection is the harness: two independent readings of the same bytes, with the second reinterpreting uncompressed layouts from the file's own masks and decoding BC1, BC2, and BC3 from the S3TC specification. That second reading stays in `tools/dds-spike/` and is how an `image_dds` upgrade or an adapter change is validated — the same role [ADR 0007](0007-parse-stellaris-source-through-a-wrapped-incremental-lexer.md) gives Jomini's tape. It has already earned its place by being wrong: its original BC3 implementation, taken from a second library, disagreed with `image_dds` on 22 real files, and the specification settled it in `image_dds`'s favour.

Three limitations are disclosed rather than closed. BC4, BC5, and BC7 are claimed by the adapter and exercised by nothing, because the pinned corpora contain none. `ConversionFailure` is unreachable from every real input and is therefore untested until a failure is injected into the encoder or the staging write. And two conformant BC decoders need not agree byte for byte — the observed disagreement is one count per channel — so the asset test suite reproduces the hashes of the pinned decoder rather than of BC decoding in general, and swapping decoders is a recipe-version change even when both are correct.
