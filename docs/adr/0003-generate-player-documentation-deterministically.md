# Generate Player Documentation deterministically

Player Documentation will be produced from the resolved content model by explicit, deterministic rules. The same supported source and generator version must produce the same documented facts, keeping the result offline-capable, reproducible, and traceable to Mod Source rather than dependent on probabilistic interpretation.

All identity-bearing data uses a versioned canonical encoding. Logical paths, registries, maps, sets, ordered script sequences, provenance, issues, and search data each have explicit normalization and ordering rules. Source numeric lexemes are preserved and calculations use exact integer or rational representations rather than binary floating point.

AI integrations may consume the generated documentation or its structured knowledge, but AI will not be required to establish the authoritative facts and relationships or to interpret raw Mod Source.

An Analysis Issue will not prevent documentation for successfully analyzed content from being generated. Partial results must carry deterministic, source-traceable completeness warnings at the Target Mod level and wherever the affected scope is known. Unsupported or failed analysis is never silently omitted or replaced with a guess.

Analysis will retain the complete known causal graph, including internal flags, variables, scripted indirection, and bookkeeping events. Player Documentation will project that graph into linked sections bounded by Player-Facing Anchors instead of flattening an arbitrarily long chain into one explanation. Requirements for an anchor remain visible and may link to their own Unlock Paths.

Every known Grant Site for a destination will be retained. The MVP creates one route card per Grant Site, combines co-located Unlock Effects from the same enclosing action, and keeps upstream branching in the linked trace. It does not attempt to decide that separate Grant Sites or reconverging branches are semantically the same route.

The MVP will not infer whether each discovered route is intended for players, AI, testing, demos, or console use. Users may hide individual routes from the normal presentation, but Hidden Routes remain part of generated knowledge and remain recoverable through a visible control. Automatic audience classification can later be layered onto the same route model.

Persistent Hidden Route identity is derived from the destination, named enclosing action, canonical player-facing anchor, direct requirements and selections, normalized unlock effects, and call-site structure. It excludes source ranges, comments, formatting, absolute paths, and localization text values, so semantically neutral source edits do not unexpectedly restore a hidden route.

MVP route presentation will emphasize concise Route Summaries, direct requirements, required selections, and the resulting unlock effect. It will not simulate an Event Chain or derive cumulative probabilities, expected outcomes, or progress bounds from its random mechanics. Those mechanics remain traceable in the technical view.

Every documented route will normalize and display its precise Unlock Effect instead of describing all terminal effects as “unlocks.” At minimum, technology routes distinguish adding a research option, adding research progress, completing the technology, and changing its Draw Weight.

Source comments are not authoritative inputs to generated facts and need not be represented in the semantic model. The app retains raw source separately and records source ranges so a bounded Source Excerpt can show the original definition and its comments in the technical view.

Statically defined scripted constants will be resolved into player-meaningful base values when the source provides one unambiguous result. The original symbol and its definition remain traceable in the technical view. Runtime-dependent, missing, or ambiguous values remain visibly unresolved rather than being guessed.
